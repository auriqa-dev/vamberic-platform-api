# Vapp portfolio interface

Vapp is Vamberic's portfolio/operator interface: Products, internal People/Organisations, Product relationships and commercial opportunities. Hive is the shared data platform. Future HVMapp and HVM marketing agents operate client marketing workspaces; sharing Hive does not grant Vapp operational access to those records.

## Scope and API compatibility

Vapp's current internal scope is records without workspaceId. Explicit workspaceId records are excluded server-side; the frontend does not receive a scope override or query Mongo. This is intentional even though schema v2 can store workspace-owned data. Product is commercial context, Workspace is operational/client scope, and Organisation is an entity. None implies the other or grants cross-client access.

Review found the existing dashboard counted all CRM documents. Its People/Organisation/Opportunity counts now use the same internal, non-archived filter as CRM lists. Product list/detail/update and dashboard Product counts explicitly exclude workspace-owned Products, preventing their exposure through the portfolio Product path. Existing Product archive/lifecycle behavior is retained. No new endpoint, HTTP contract, OpenAPI/client generation, Mongo schema change or live database operation was needed.

Current response contracts do not expose organisation website/industry, opportunity owner/expectedCloseAt, generic organisation activity, or Product-level subscriptions/entitlements/events/all relationships. These are deliberately not fabricated or shown as “not recorded” when the API cannot tell us. Linked people are not labelled primary contacts. The Subscriptions page was only a placeholder, so no subscription functionality was removed. A future narrow internal read projection can add these fields when there is a clear Vapp use case. Human-only CRM owner means accountable human; agents/Queen/system are action actors, not record owners.

## HVM and research boundaries

Future pattern: **raw workspace data → authorized HVMapp / HVM agents → authorized reporting summaries/projections → Vapp portfolio oversight**. Vapp must not query raw client records to construct those summaries. Future reporting needs explicit grants, defined metrics and freshness; this refactor adds no HVM placeholder metrics.

Campaign operations, Lead Gen, client CRM, ICPs, advertising, swarms, approvals, client dashboards and agent controls belong to future HVMapp. No such screens are added. Lead Gen research is upstream of CRM; crm_leads begins at deliberate commercial qualification. crm_leads/crm_tasks stay backend-only pending a genuine authorized use case. No workspace management, all-workspaces endpoint or hidden override exists.

## Validation

Normal checks use the available repository scripts: `pnpm --filter @workspace/api-server run lint`, `pnpm run typecheck`, `pnpm --filter @workspace/api-server run test`, `node scripts/deploy/test-client.mjs`, `node --test scripts/deploy/release.test.mjs`, `PORT=3000 BASE_PATH=/ pnpm run build`, API format check, Prettier on changed frontend/docs files and `git diff --check`.

New rendered-component tests cover navigation, genuine empty states, contextual Product relationships, opportunity subjects/stage/value and unknown versus zero value. API regression coverage verifies internal counts, workspace Product exclusion (including PATCH), workspace delete-preview rejection and existing Cognito gating. Existing enquiry, scope and hard-delete suites remain required. Tests use local fixtures, never live client data.

Recommended next task: define and implement HVMapp's trusted application/actor/workspace authorization boundary and scoped ingestion rules before exposing workspace operations. A separate Vapp task can add a minimal internal opportunity-owner/expected-close projection; neither should bypass scope filtering.
