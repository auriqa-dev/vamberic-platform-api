# Public product enquiries

`POST /api/v1/public/products/:productId/enquiries` accepts enquiries for any existing, non-archived, non-retired Product. The website supplies the Product's immutable `product_…` ID from Vapp. It does not send a product name, Mongo ID, Cognito token or Offer ID. No HVM identifier is built into the service.

This endpoint is intentionally unauthenticated. Existing private routes still require a verified Cognito access token. No separate leads database or collection, Offers system, full Leads UI, website changes or infrastructure changes are included.

## Contract

Send `Content-Type: application/json`. The entire body is limited to **16 KiB**, compressed bodies are not accepted, unknown properties are rejected, and strings are trimmed before validation. Optional values should be omitted rather than sent as empty strings or null.

| Field                                             | Required    | Limit / meaning                                                                                          |
| ------------------------------------------------- | ----------- | -------------------------------------------------------------------------------------------------------- |
| `name`                                            | Yes         | 100 characters; full name; single-word names accepted                                                    |
| `workEmail`                                       | Yes         | Valid email, at most 254 characters; no inference from whether the provider is a business email provider |
| `company`                                         | Yes         | 300 characters                                                                                           |
| `message`                                         | Yes         | 4,000 characters of plain text                                                                           |
| `website`                                         | No          | 253 characters; domain or HTTP(S) website; credentials, IP addresses and non-default ports rejected      |
| `jobTitle`                                        | No          | 200 characters                                                                                           |
| `serviceInterest`                                 | No          | 200 characters; submitted attribution text, not an Offer ID                                              |
| `marketingOptIn`                                  | No          | Boolean; only explicit `true` can record positive consent                                                |
| `marketingConsentText`                            | With opt-in | 1,000 characters; exact wording displayed to the visitor                                                 |
| `marketingConsentVersion`                         | With opt-in | 100 characters; website's wording version                                                                |
| `source`, `medium`, `campaign`, `content`, `term` | No          | Each 200 characters; UTM-style labels, not trusted internal IDs                                          |
| `landingPage`, `referrer`                         | No          | Each 1,000 characters; HTTP(S) URLs without credentials                                                  |

Encoded consent text/version together are limited to 1,700 JSON characters so the complete evidence fits the existing 2,000-character permission evidence field. The server validates domain/URL semantics and conditional consent requirements in addition to the generated contract. Website domains are lowercased, converted by the URL parser to their ASCII representation, and stripped of a leading `www.`. No URL is fetched. Page/referrer query strings and fragments are removed before storage to avoid retaining URL tokens; send needed campaign attribution through the dedicated fields.

Success is HTTP **201**:

```json
{
  "status": "received",
  "enquiryId": "event_00000000000000000000000001"
}
```

The actual event identifier is generated by the API. No Person, Contact Point or Organisation information is returned. Errors use `{ "error": { "code": "…", "message": "…" } }`: 400 invalid input/JSON, 403 unapproved Origin, 404 unavailable Product, 409 an identity/organisation that cannot be resolved safely, 413 payload too large, 415 unsupported content type/encoding, 429 rate limited (with `Retry-After`), or 503 temporarily unavailable. Responses never contain submitted values, raw Mongo errors or stack traces. Responses use `Cache-Control: no-store`.

## Shared CRM mapping

All records use the existing application ID generator and Zod persistence schemas. New records have `source.system=public_enquiry` and server-generated timestamps.

| Existing collection          | Mapping                                                                                                                                                          |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `products`                   | Look up the supplied ID, reject archived/retired/missing products; do not update Product                                                                         |
| `people`                     | Reuse through normalized email Contact Point; otherwise create first name, optional surname and full `displayName`                                               |
| `contact_points`             | Trim/lowercase email using the central normalizer. New contacts are primary email, validity/deliverability unknown; submission does not verify ownership         |
| `organisations`              | Reuse only exact whitespace-normalized company name plus canonical website domain; otherwise create a prospect                                                   |
| `organisation_relationships` | Reuse an equivalent non-archived current person–organisation relationship without an end date; otherwise create one with the submitted job title                 |
| `product_relationships`      | Reuse a non-ended, non-archived relationship for the same Product, Person and Organisation; otherwise create `engaged`. Never downgrade a current customer       |
| `opportunities`              | One per accepted submission: target Product, Organisation and Person, `status=open`, `stage=enquiry`. No amount, currency, probability or fictitious campaign ID |
| `events`                     | Append-only `enquiry_submitted`, server `occurredAt`, Product/Person/Organisation IDs and a bounded, explicitly constructed payload                              |
| `marketing_permissions`      | Append-only consent decision only for explicit opt-in with evidence                                                                                              |

The only CRM schema extension is making `Person.lastName` optional, so a single-word name is not given an invented surname. For multi-word input, the first token is stored as first name and the remaining tokens as surname; the submitted full name always remains in `displayName` and the event. Existing Person identity fields are not overwritten by public input.

The Event payload holds `opportunityId`, form name/version, submitted name/email/company/message, website domain, job title, service interest, the five attribution labels, sanitized page/referrer, and whether opt-in was explicit. These fields are needed to review and fulfil the enquiry and are private CRM data. Do not render text as HTML or publish these events in a public feed. Tokens, headers, IP addresses and raw request objects are not persisted. Campaign labels are not turned into internal Campaign IDs. The event-to-opportunity link preserves attribution without adding another opportunity type or Offer model.

Existing Vapp data structures and dashboard counts can surface these records. No People/Organisations/Opportunities/Events screens or notification delivery are added by this change.

## Deduplication, concurrency and failure handling

- One unambiguous email contact is reused across Products. Multiple matching contact points, missing/archived/inactive owners or a contact marked as having left its organisation return a generic 409; the API does not merge identities or disclose their details.
- Existing contact ownership, names, primary designation, suppression, validity and deliverability remain unchanged. Its modification timestamp is advanced inside the transaction to serialize repeat submissions for that identity.
- With a website, both canonical domain and exact company name must match. There is no fuzzy matching, email-domain inference or name-only global merge. Multiple exact matches are rejected for review.
- Without a website, the API can reuse a same-name organisation only through this Person's current organisation relationship. Otherwise it creates a prospect. Two different people supplying the same name without domains can therefore create distinct organisations intentionally.
- Separate submissions create separate Opportunities and Events. There is no submission-level idempotency key in v1: an uncertain network result followed by a retry can create a second enquiry, but not another Person for that email. The website should disable its submit button while a request is pending.
- All writes, including event and consent, occur in one Mongo transaction with snapshot reads and majority write concern. Unsupported transactions fail closed; there is no non-transactional fallback. Partial failures roll back CRM records. The driver retries transient transaction conflicts; duplicate-key first-insert races restart the full transaction up to two further times.

Two narrowly scoped partial unique indexes are declared through the existing database setup definitions:

| Collection       | Index                         | Keys / scope                                                                                |
| ---------------- | ----------------------------- | ------------------------------------------------------------------------------------------- |
| `contact_points` | `public_enquiry_email_unique` | `(normalizedValue, source.system)`, only email contacts with `source.system=public_enquiry` |
| `organisations`  | `public_enquiry_org_unique`   | `(domain, name, source.system)`, only public-enquiry organisations with string domains      |

These protect concurrent creation by this ingestion route across API replicas, while preserving existing CRM semantics that allow shared email addresses. Other ingestion paths must resolve identities consistently; these are not global email uniqueness constraints. Required index definitions are checked before enquiry writes, and missing/incompatible indexes return 503. Indexes are never created by an HTTP request. The existing setup duplicate check was adjusted to handle dotted index keys safely in aggregation.

## Marketing permissions

An enquiry grants no automatic marketing permission. Absent/false opt-in adds no permission and does not revoke or overwrite an existing decision. Service fulfilment contact is not recorded as marketing consent.

Explicit true requires both `marketingConsentText` and `marketingConsentVersion`. The appended decision uses the Person and Contact Point, target Product, `portfolioWide=false`, `channel=email`, `purpose=marketing`, `lawfulBasis=consent`, `permitted=true`, and server `effectiveAt`. Evidence records the public form source, wording, version and enquiry Event ID. Repeated explicit opt-ins append decisions; historical decisions are never updated. Contact suppression is not cleared.

The website must supply the wording actually displayed, its version, and true only when the visitor explicitly chooses to opt in. This is a submitted consent claim with provenance, not proof of mailbox ownership. No confirmation email or double-opt-in workflow is implemented.

## CORS, rate limiting and logging

Existing authenticated Vapp `CORS_ORIGINS` rules remain separate. Configure the backend, not a `VITE_*` variable:

```dotenv
PUBLIC_ENQUIRY_CORS_ORIGINS=https://h-v-m.agency
PUBLIC_ENQUIRY_RATE_LIMIT_MAX_REQUESTS=5
```

For explicitly enabled local development, include an exact origin such as `http://localhost:3000` in that comma-separated list. Empty configuration grants no browser origin access. Wildcards, credentials and path-bearing origins are rejected by configuration validation. Public preflights allow POST and Content-Type only, with no credentials. Actual requests with an unapproved Origin are rejected before persistence; approved product origins do not gain CORS access to private routes. The list is shared across this public endpoint for all Products, not a Product-specific origin-to-ID authorization map.

Server-to-server requests without Origin are allowed. CORS is a browser policy, not caller authentication: scripts can forge or omit Origin. The tighter public limiter defaults to 5 requests per client IP per 60 seconds (configurable 1–20), separate from the normal default 100/minute. Like the existing limiter, counters are per API process and reset on restart. Use the existing one-trusted-proxy topology; direct public exposure with spoofable forwarded headers or multiple replicas may need gateway/distributed abuse controls later.

Helmet still runs before the public router. The router is mounted before the Cognito middleware and terminates only its new public namespace; existing private authentication is unchanged. Public request logs contain only method and a fixed `/api/v1/public` label (plus normal status/timing), not dynamic IDs, query strings, form fields, headers or incoming request IDs. Failure logs contain a fixed error code only.

A dependency-injected `enquirySpamCheck` hook runs after validation and before any CRM lookup/write. A future challenge provider can be added there, alongside explicitly bounded request fields and an OpenAPI update if a challenge token is needed. There is no CAPTCHA, honeypot dependency or external provider call in v1.

## HVM integration example

The HVM website is unchanged. The owner supplied HVM's Product ID for the deployment handoff: **`product_01m2wffbf3p9p19d3nd1s2fp3x`**. It has not been re-queried against live MongoDB in this readiness task. Store it in the website's integration configuration, not in generic API logic.

Exact HVM endpoint:

```text
POST https://api.vamberic.com/api/v1/public/products/product_01m2wffbf3p9p19d3nd1s2fp3x/enquiries
```

The website can use the following request:

```js
const productId = "product_01m2wffbf3p9p19d3nd1s2fp3x"; // HVM website configuration
const response = await fetch(
  `https://api.vamberic.com/api/v1/public/products/${productId}/enquiries`,
  {
    method: "POST",
    credentials: "omit",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      name: "Alex Example",
      workEmail: "alex@example.com",
      company: "Example Ltd",
      website: "example.com",
      message: "I'd like to discuss AI visibility for our business.",
      serviceInterest: "AI Visibility",
      marketingOptIn: false,
      source: "website",
      medium: "organic",
      landingPage: "https://h-v-m.agency/enquire",
    }),
  },
);
const result = await response.json();
if (!response.ok) {
  // Show a safe error; respect Retry-After on 429.
  throw new Error(result.error?.message ?? "Unable to send enquiry");
}
// Show acknowledgement. Never expose internal CRM information.
```

The generated `submitPublicEnquiry` operation is an alternative to raw fetch. Its dedicated public mutator omits auth headers and cookies even when a Vapp token getter is configured. Private generated operations keep their existing token behavior. Configure the normal client base URL when calling a remote API.

## Deployment readiness review

No live MongoDB connection, index provisioning, AWS/CDK change, deployment, commit or push was performed. The code is ready to commit and build into a new API image. Index provisioning and rollout remain conditional on a successful live preflight in a separately authorized task.

The exact index specifications are shared by the runtime guard and canonical `COLLECTION_DEFINITIONS` in `src/db/collections.ts`:

```json
[
  {
    "collection": "contact_points",
    "name": "public_enquiry_email_unique",
    "key": { "normalizedValue": 1, "source.system": 1 },
    "unique": true,
    "partialFilterExpression": {
      "type": "email",
      "source.system": "public_enquiry"
    }
  },
  {
    "collection": "organisations",
    "name": "public_enquiry_org_unique",
    "key": { "domain": 1, "name": 1, "source.system": 1 },
    "unique": true,
    "partialFilterExpression": {
      "domain": { "$type": "string" },
      "source.system": "public_enquiry"
    }
  }
]
```

Neither specifies `sparse` (default false). Both are partial indexes. Existing documents outside the filters, including ordinary legacy/imported contacts and organisations, receive no new uniqueness constraint. Domain-less organisations are excluded from the organisation index. Documents already inside these filters must satisfy uniqueness; this has not been assumed or checked against live data. Index creation never merges, rewrites or deletes existing domain documents. Conflicting existing definitions and duplicate risks require review.

Use only the existing canonical setup path, with the intended server environment supplied:

```sh
pnpm --filter @workspace/api-server db:setup --dry-run
# After reviewing and approving the complete preflight:
pnpm --filter @workspace/api-server db:setup --apply
```

The dry-run reports missing indexes and duplicate diagnostics without mutations. The readiness review added a pre-write guard so apply refuses both confirmed duplicates and cases where duplicate inspection is unavailable, before creating collections/indexes/metadata. MongoDB's unique index build remains the final protection against a concurrent duplicate inserted after preflight. Setup manages all canonical resources and schema metadata, not just these two indexes; inspect the entire plan for unexpected changes before applying. No separate migration mechanism is needed or added.

`build.mjs` already bundles `db-setup.mjs`, and the Dockerfile copies the complete `dist` directory into the Node 24 runtime image. The runtime image does not contain pnpm/source files. To use a one-off ECS task from the **newly built image**, override its command with the appropriate existing bundled command:

```sh
node --enable-source-maps dist/db-setup.mjs --dry-run
# Only after approved preflight:
node --enable-source-maps dist/db-setup.mjs --apply
```

That task must retain the API's intended MongoDB secret injection, network connectivity and validated server configuration. MongoDB must support transactions, and the runtime database role must permit index inspection and the required CRM reads/writes. Provisioning requires the existing setup role's index/collection permissions. These deployment permissions and network settings were not changed or verified live.

Public-origin runtime configuration is independent:

```dotenv
PUBLIC_ENQUIRY_CORS_ORIGINS=https://h-v-m.agency
```

Multiple origins use a comma-separated string, for example `https://h-v-m.agency,http://localhost:3000`. There is no wildcard matching; readiness hardening additionally rejects wildcard-shaped hostnames such as `https://*.example.com`. Normal Vapp origins remain in `CORS_ORIGINS`. Local infrastructure source currently supplies `https://app.vamberic.com,http://localhost:5173` for Vapp and does not yet inject the new public variable. Add the public variable separately to the API container environment in ECS/CDK during the authorized infrastructure/configuration change; do not append HVM to the Vapp allowlist. Application support is ready; that external configuration change is still pending.

This review changed only deployment safeguards and their regression tests: the unique-index-risk refusal in `db/setup.ts`, wildcard-host rejection in `config.ts`, and tests in `domain.test.ts`/`public-enquiries.test.ts`, plus this handoff documentation.
