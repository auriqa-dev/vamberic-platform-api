## Decisions for review before build

Approve an implementation scope, not individual tool calls in isolation:

- Keep current runtime/control plane and implement NBA as a finite, event/due-time-driven agent with acquisition and managed-contact modes.
- Make Communications a deterministic service; keep content generation and reply interpretation as bounded capabilities.
- Include Library ingestion/CTA validation, email drafting, preview and single-contact testing in the first outbound increment.
- Evaluate React Email/MailParser first; reserve AI SDK/assistant-ui for the new Interaction slice. No wholesale framework migration.
- Agree the initial campaign's approval and autonomy boundaries, sending windows/pacing, identity/engagement ownership and qualification/meeting handover. These must be configurable per client, not hard-coded to Odyssiant.
- Authorise any future live test batch/deployment separately with exact recipients, records, provider actions, recovery and acceptance checks. This audit does not send anything or activate campaigns.

## Architectural conflicts to avoid

A framework's built-in call cap must not reintroduce arbitrary HVM AI quotas. Keep bounded retries and loop detection. Graph checkpoints cannot become a second canonical store conflicting with Hive approvals. Generic provider selection cannot bypass a client's Lusha/account consent. A public conversational agent cannot inherit Henry operator authority. Framework “human-in-the-loop” is not a substitute for HVM's specific approval semantics. None of these constraints warrants removing useful safeguards for speed.
