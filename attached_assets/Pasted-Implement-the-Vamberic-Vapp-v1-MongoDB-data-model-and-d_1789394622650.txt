Implement the Vamberic Vapp v1 MongoDB data model and database setup framework.

Context

Vapp is the private Vamberic operating application that will eventually run at app.vamberic.com. It will be used to manage the portfolio of Vamberic products, CRM, customers, organisations, campaigns, subscriptions, revenue, activity and later software agents.

Architecture:

Vapp → Vamberic Platform API → MongoDB Atlas

Only the Platform API may access MongoDB. Vapp and future product applications must never connect directly to MongoDB.

The existing API already:

uses Node.js + TypeScript + Express
uses the official MongoDB Node.js driver
reads MONGODB_URI from runtime configuration
has /health and /ready
successfully connects to the Atlas database vamberic_studio

Do not use Mongoose.

Objective

Define and implement the complete Vapp v1 core MongoDB collection architecture in one pass, including:

TypeScript domain types
Zod validation
MongoDB collection access
collection creation/bootstrap
indexes
safe schema/version management
tests

Do not build the CRM UI or full CRUD API yet.

Collections

Implement these collections:

1. products

Vamberic-owned products/apps.

Include concepts such as:

stable product ID
name
slug/code
description
lifecycle status: idea / validation / active / paused / retired
product type
domains
commercial model
one-off purchase available
subscription available
currency
internal notes
created/updated/archive metadata

Product examples later may include Energy Health Check and other Vamberic micro-products.

2. people

Canonical human records.

Important principle:

An email address is not the person.

A person must survive:

employer changes
email changes
multiple products
multiple contact points

Include:

stable person ID
first/last/display name
role/title where appropriate as current descriptive data only
source/provenance
lifecycle metadata
timestamps
archived state

Do not embed the canonical email address as the identity key.

3. contact_points

Email addresses and later phone/contact channels associated with people.

Include:

soft bounce / hard bounce
invalid
left organisation
suppressed
source
first seen / last validated
timestamps

An email address that becomes invalid or belongs to a person who left an organisation must be invalidated without deleting the person or their history.

6. product_relationships

Include:

Design this so one person or organisation can have different relationships with different Vamberic products.

7. marketing_permissions

Keep this separate from CRM lifecycle.

Include:

Preserve history rather than simply overwriting opt-in state.

Do not attempt to encode legal advice into application logic. Build an extensible policy-driven data model.

Common data-model rules

Establish a consistent convention across collections for:

stable application-generated IDs independent of Mongo _id
createdAt
updatedAt
archive/delete state where appropriate
schema version
source/provenance

Prefer immutable IDs.

Use UTC dates.

Do not duplicate large person/organisation objects inside relationship collections. Store references and deliberately denormalize only small display fields when there is a documented performance reason.

Do not implement multi-tenancy unnecessarily. This is currently one Vamberic business operating multiple products.

Product boundaries must nevertheless be explicit wherever relevant.

Validation

Use Zod as the application validation layer.

Define:

domain schemas
insert/create schemas
update schemas where useful

Keep database persistence types separate from public API DTOs where appropriate.

Do not expose Mongo _id as the public identity.

MongoDB collection bootstrap

Add an idempotent database setup mechanism, for example:

pnpm db:setup

or an equivalent command consistent with the repository structure.

It must:

connect using existing runtime Mongo configuration
create missing collections
create/update required indexes safely
be idempotent
not delete production data
not drop collections automatically
fail safely if an incompatible destructive migration would be required

Do not rely purely on Mongo creating collections implicitly on first insert.

Create a small metadata collection such as:

schema_versions

or equivalent to track applied database schema/setup versions.

Indexing

Design appropriate indexes now.

Include where relevant:

unique application IDs
normalized email/contact values
product IDs
person IDs
organisation IDs
external provider IDs
lifecycle/status fields used for filtering
event timestamps
event type + product/time combinations
campaign references
transaction external IDs

Avoid excessive speculative indexes.

Document index reasoning.

app.vamberic.com

email sending
Lusha integration
Paddle integration
analytics dashboards
agents

Those will follow.

Initial API scope

It is acceptable to expose no new business endpoints in this change.

If useful for architecture/tests, only add minimal internal repository/service layers for:

products
people
organisations

Do not turn this into a full CRM API implementation.

Testing

Add tests covering:

Zod validation for each collection
required/invalid identifiers
relationship integrity at application level
index definitions
idempotent database setup
repeated setup does not destroy/change existing data
safe failure behaviour
no credential leakage in logs/errors

Tests should not require the live Atlas database.

Use appropriate mocks/test containers/in-memory approach compatible with the repository.
